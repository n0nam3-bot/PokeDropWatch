# PokéDrop Watch — Configuration and Change Guide

**Current release:** 1.4.0  
**Last updated:** 2026-11-17

This is the canonical development reference. Read it before editing the repository. It records the current architecture, exact configuration locations, customization rules, tests, and the ZIP patch release process.

## 1. Non-negotiable project rules

1. Inspect the current repository files and tests before changing anything. The checked-out project is the source of truth; old chat notes and ZIPs are not.
2. Never guess at settings, retailer capabilities, product release dates, email behavior, or completed roadmap work. Separate tested behavior from assumptions and live-service limitations.
3. Make only the changes required by the request. Preserve existing functionality and `docs/data/state.json` unless a tested migration is needed.
4. Keep the public site free to host on GitHub Pages, the monitor on GitHub Actions, subscriber records in Firestore, and the private verification/admin API in Apps Script. No Google Sheet is used. Do not add a paid dependency or AI service unless explicitly approved.
5. Never expose service-account JSON, Gmail App Passwords, HMAC secrets, admin passwords, subscriber emails, or private delivery state in public files or logs.
6. A retailer is not “working” because its URL is configured or because it returned HTTP 200. It must return real Pokémon entries that the parser extracts and the live scan must confirm it.
7. A listing's first observation time is not its release date or seller listing date. Use **FIRST SEEN** unless a reliable release/drop date and validation rule exist. Do not send first-seen products as “new drop” emails.
8. Run all tests after changes. Add regression tests for every fixed bug. Do not delete or weaken tests to obtain a pass.
9. Update this guide, README, roadmap, and changelog together when the architecture, configuration, features, or status changes.
10. Deliver a small ZIP containing only changed files, verify its contents and clean-copy installation, and list every modified path.

### Authentication architecture — do not reintroduce Firebase Auth

- v1.4.0 does **not** import Firebase Authentication in the public browser.
- Admin email/password verification and password-reset codes are handled by Apps Script using private Script Properties and HMAC hashes.
- Subscriber email verification and unsubscribe confirmation use six-digit codes sent through Apps Script MailApp and entered on the same page.
- Firestore is the subscriber database. The website cannot access subscriber documents directly. `firebase/firestore.rules` denies all browser reads/writes; Apps Script/GitHub Actions use a service account through Google IAM.
- `docs/firebase-client.js` is a retired no-op compatibility stub. Do not add Firebase SDK imports or use it for admin login. `docs/firebase-config.js` is legacy public web configuration and is not used by the current auth flow.
- If Firebase `noreply@...firebaseapp.com` emails still arrive after a release, check whether the browser is serving an old `admin.js` or the Apps Script project still runs an old deployment. GitHub Pages and Apps Script are separately deployed.

### 3.3 Public configuration

`docs/subscription-backend-config.js` contains only the public Apps Script `/exec` URL. The URL is not a secret. Never add HMAC secrets, service-account JSON or Gmail credentials to this module.

`docs/firebase-client.js` is a retired no-op stub. Keep it free of Firebase SDK imports. The website uses no Firebase Auth sign-in, no Firebase password-reset actions, and no Firebase auth email templates.

### 3.4 Firestore

`firebase/firestore.rules` must remain deny-all for browser/client requests. Apps Script and the GitHub Actions monitor access the database using the private service-account identity and Google IAM. Never weaken the client rules to make a browser operation work.

## 4. Source configuration and parser behavior

The monitor reads `config/sources.json`.

### Supported `settings`

| Setting | Default | Behavior |
|---|---:|---|
| `check_interval_minutes` | `15` | Documentation/display only; workflow cron sets schedule |
| `request_timeout_seconds` | `25` | Per-URL HTTP timeout |
| `max_items_per_catalog` | `80` | Maximum products retained per source scan after deduplication |
| `history_limit` | `100` | Recent events retained in public state |
| `email_digest_subject_prefix` | `PokéDrop Watch` | Email subject prefix |
| `user_agent` | `PokeDropWatch/1.0...` | HTTP request User-Agent; the monitor falls back to a browser-like agent if this custom value is the old default |

### Source object fields

| Field | Required | Rule |
|---|---|---|
| `id` | Yes | Stable unique ID. Do not casually rename; IDs key saved state. |
| `name` | Yes | Display name for source status. |
| `retailer` | Yes for catalog | Retailer label used for grouping and preferences. |
| `retailer_key` | Recommended | Stable key used by client filters and subscriber preferences. |
| `type` | Yes | `catalog`, `product`, or `rss`. |
| `url` | Yes | Primary public HTTP/HTTPS page/feed. |
| `alternate_urls` | Optional | Up to three extra public search/page URLs. They are fetched and merged into one source result. |
| `enabled` | Recommended | `true` to scan; `false` to disable without deleting its saved configuration. |
| `category` | Optional | Preferred fallback product category or `news`. |
| `notes` | Optional | Plain-language limitations shown in source diagnostics. |

The scanner supports Schema.org JSON-LD, embedded JSON/SPA hydration blocks, direct JSON responses, qualifying product card links/images and RSS/Atom. It does not run a full browser, execute page JavaScript, bypass login/CAPTCHAs/queues, or evade anti-bot controls. If a page needs browser rendering or blocks requests, it remains `NO MATCH` or `ISSUE` until a permitted dedicated source adapter/data feed is implemented.

A source may have up to four URLs total: `url` plus three `alternate_urls`. All successfully fetched result bodies are merged, filtered for Pokémon-relevant titles, and deduplicated by retailer plus normalized product title. `MATCHES` means one or more relevant records were actually extracted; `NO MATCH` means pages responded but no supported product/feed entries were recognized; `ISSUE` means all configured URLs failed.

### Product identity, event rules and history

- Amazon product URL variants for the same ASIN should normalize to `/dp/ASIN`.
- Duplicate product cards with the same normalized title/retailer should collapse; prefer the record with a real image, price, known availability and SKU.
- TCG classification must recognize terms including Pokémon TCG, trading cards, boosters, Pokémon Card Game, card sleeves, and relevant set/product names. Explicit Nintendo/console game terms take precedence and classify as `games`.
- Newly discovered catalog entries are `first_seen`, not `new_drop`. They are not emailed. A genuine restock requires a saved out-of-stock → in-stock/preorder transition. A price drop/change requires comparable prices from the source. News is handled as a separate event type.
- At monitor startup, legacy `new_drop` history is converted to `first_seen`, duplicate first-seen records are collapsed, and first-seen events are removed from pending email. Keep saved `docs/data/state.json` so baseline transitions remain meaningful.

### Safe retailer adapter procedure

1. Confirm the retailer page can be opened publicly without bypassing access controls.
2. Save a sanitized representative HTML/JSON/XML fixture to a new test fixture path. Remove cookies, session tokens, personal addresses, and other private values.
3. Write a retailer-specific parser only when generic JSON/structured-data/card parsing cannot handle the fixture.
4. Add tests for title, URL, image, price, availability, irrelevant result rejection and duplicates.
5. Add/update the source in `config/sources.json`; use `alternate_urls` only for known public URLs, not guessed URLs.
6. Run the full test suite and a controlled live GitHub Actions scan. Only then mark that retailer integration complete in the roadmap.

Do not promise all sources will work: retailer HTML, bot restrictions and API access can change. A `NO MATCH` is not evidence that no Pokémon item is in stock.

## 6. Email and subscriber behavior

`backend/apps-script/Code.gs` controls OTP/admin auth and `monitor/subscribers.py` handles individual approved-subscriber delivery. `monitor/engine.py` formats owner alert digests.

- Verification and admin-reset codes are six digits, expire after 10 minutes, allow at most five attempts and are single use.
- The Apps Script code enforces a 60-second cooldown, up to three requests per email per hour, and a 25-email daily code cap. Google MailApp quota also applies.
- Admin login uses email/password via Apps Script; reset uses an emailed code entered on the same admin page. It does not call Firebase Auth.
- Subscriber application requires verified email ownership and then awaits admin approval. Unsubscribe requires an emailed code and explicit confirmation; it does not require admin approval.
- Only approved/active subscribers receive notifications. Emails are sent individually; do not expose recipients through To/CC lists.
- Subscriber emails, IDs and pending delivery records are private Firestore data and must not be written into `docs/data/state.json` or public workflow logs.
- Product discovery is not a new-drop notification. Only observed restocks, price drops/changes, and news are eligible for automated product emails.
- Never log SMTP credentials, OTPs, reset codes, passwords, service-account JSON, subscriber emails or session tokens.

## 7. Tests and release validation

Run from repository root:

```bash
python -m pip install -r monitor/requirements.txt
python -m unittest discover -s tests -v
python -m py_compile monitor/*.py tests/*.py
python -m json.tool config/sources.json > /dev/null
```

For JavaScript syntax, use Node if available:

```bash
node --check docs/app.js
node --check docs/admin.js
node --check docs/subscriptions.js
node --check docs/firebase-client.js
```

`docs/admin.js` and `docs/subscriptions.js` are ES modules; depending on the installed Node mode, `node --check` may require a temporary `.mjs` copy or `--input-type=module`. Do not treat a tooling-mode error as a source syntax error without checking accordingly.

Before release:

- Run all unit tests; record exact pass count.
- Validate JSON and Python compilation.
- Validate HTML/JavaScript links and DOM IDs.
- Inspect the complete changed-file list.
- Apply the patch ZIP to a clean copy using `scripts/apply_patch.py`.
- Verify there are no wrapper folders, unsafe paths, or unintended files.
- Test desktop and narrow phone layout manually.
- Test source parsing from fixtures; a unit test is not live retailer verification.
- State clearly which integrations still require Firebase/Gmail credentials or a live Actions scan.

Do not run `python monitor/run.py` unintentionally: it performs live network requests, updates `docs/data/state.json`, and can send mail when secrets are present.

## 8. ZIP patch rules

- Use repository-relative paths in the ZIP, for example `docs/app.js`, `monitor/engine.py`, `config/sources.json`.
- Include only changed/new files. Do not include `.git/`, `.github/workflows/`, generated `__pycache__/`, local secrets, or the whole repository for a small update.
- The existing GitHub workflow detects uploaded ZIPs recursively (including under `updates/`), validates archive paths, extracts them into repository locations, commits the changed files and then runs the monitor.
- `.github/workflows/` is protected by the patch installer. Any workflow change is a separate direct GitHub edit.
- Apps Script runs outside GitHub. A ZIP can update the source files under `backend/apps-script/`, but the owner must copy those files into the existing Apps Script project and deploy **Manage deployments → Edit → New version → Deploy**.
- Keep the ZIP name versioned and update `docs/CHANGELOG.md`, newest release at top. Update `docs/ROADMAP.md` with checkboxes only when evidence supports completion.
